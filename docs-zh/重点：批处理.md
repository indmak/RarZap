加入批量处理功能后，技术栈的核心变化在于**任务调度与并发控制层**的引入。以下是完善后的完整方案。

---

## 一、批量处理架构设计

批量转换的核心挑战不是"能不能并发"，而是**如何在保持 UI 流畅的前提下，安全、可控地调度多个 CPU 密集型任务**。

### 1.1 整体架构

采用**生产者-消费者模型**，分三层：

```
UI 层（GPUI 主线程）
  │  提交任务 / 接收进度 / 更新状态
  ▼
调度层（BatchScheduler）
  │  任务队列 + 并发信号量 + 取消令牌
  ▼
执行层（后台 Worker 线程池）
  │  RAR 解压 → ZIP 打包（CPU 密集型）
  ▼
结果层（mpsc channel 回传）
```

每个 RAR→ZIP 转换作为**独立任务（Job）** 处理，任务之间互不依赖，天然适合并行。这正是 `oximedia-batch` 等批量处理框架采用的 Job Queue + Worker Pool 模式。

### 1.2 任务状态机

每个任务有明确的状态流转：

```
Pending → Running → (Completed | Failed | Cancelled)
```

- **Pending**：已加入队列，等待 worker 槽位
- **Running**：正在执行解压/打包
- **Completed**：输出文件已成功写入
- **Failed**：出错（源文件损坏、目标路径无权限等），记录错误信息
- **Cancelled**：用户手动取消或程序退出时中断

UI 层通过 `DataTable` 展示每个任务的状态列，用不同颜色标记。这是批量工具的标准交互模式。

## 二、并发控制策略

### 2.1 并发模型：异步任务池 + 信号量限流

**不要用 rayon 做外层批量调度。** rayon 适合单个任务内部的并行（如一个 ZIP 内多个文件并行压缩），但批量任务调度需要**细粒度的取消和进度控制**，rayon 的 work-stealing 模型在这方面的控制力不足。

推荐方案：**Tokio 异步运行时 + `Semaphore` 限流**。

```toml
[dependencies]
tokio = { version = "1", features = ["rt-multi-thread", "sync", "time"] }
tokio-util = { version = "0.7", features = ["rt"] }
```

核心调度逻辑：

```rust
use tokio::sync::Semaphore;
use std::sync::Arc;

pub struct BatchScheduler {
    semaphore: Arc<Semaphore>,
    cancel_token: CancellationToken,
}

impl BatchScheduler {
    pub fn new(max_parallel: usize) -> Self {
        let max = max_parallel.max(1);
        Self {
            semaphore: Arc::new(Semaphore::new(max)),
            cancel_token: CancellationToken::new(),
        }
    }

    pub async fn submit(&self, job: ConversionJob) -> JobResult {
        let _permit = self.semaphore
            .clone()
            .acquire_owned()
            .await
            .expect("semaphore closed");

        // 检查是否已被取消
        if self.cancel_token.is_cancelled() {
            return JobResult::Cancelled;
        }

        // 在阻塞线程上执行 CPU 密集型转换
        tokio::task::spawn_blocking(move || {
            convert_rar_to_zip(&job.rar_path, &job.zip_path)
        })
        .await
        .unwrap_or_else(|e| JobResult::Failed(format!("Task panic: {}", e)))
    }
}
```

**并发数建议：** `max_parallel = num_cpus::get()` 或略低于核数（留 1 核给 UI 渲染）。对于压缩这种 CPU 密集型任务，超线程带来的收益有限，建议 `max_parallel = physical_cores`。

### 2.2 单任务内部并行：rayon

虽然外层用 Tokio 调度，但**单个 ZIP 的打包过程**可以内部用 rayon 并行压缩多个文件条目。`ripzip` 的基准测试显示，rayon + flate2(zlib-rs) 并行压缩比标准 `zip` crate（单线程 miniz_oxide）快 **2.0–10.7 倍**，且速度提升与单文件大小正相关。

```toml
[dependencies]
rayon = "1"
flate2 = { version = "1", features = ["zlib-rs"] }  # 使用 zlib-rs 后端
```

如果你不想自己实现并行 ZIP 压缩，可以直接使用 **`mtzip`**（多线程 ZIP 库，支持 rayon feature）或 **`ripzip`**（并行压缩 + 原子写入 + ZIP64 + Zstd 支持）。

**双层并发的风险：** 外层 Tokio 并发数 × 内层 rayon 线程数可能超过 CPU 核数，导致上下文切换开销。建议：
- 如果外层并发数 = 核数，内层 rayon 限制为 1–2 线程
- 或者外层并发数 = 核数 / 2，内层 rayon 使用全部核数

## 三、进度报告与 UI 通信

### 3.1 GPUI 的异步任务模型

GPUI 提供了两套 spawn API：

- **`cx.spawn()`** — 前台任务，运行在 UI 线程，可以更新 Entity 状态
- **`cx.background_spawn()`** — 后台任务，运行在 worker 线程，**不能直接更新 Entity**

关键规则：**所有 UI 更新必须在前后台任务之间链式切换**。后台任务完成后，通过 `.then(cx.spawn(...))` 回到前台更新状态：

```rust
cx.background_spawn(async move {
    // CPU 密集型转换，在后台线程执行
    convert_rar_to_zip(&rar_path, &zip_path)
})
.then(cx.spawn(move |result, cx| {
    // 回到 UI 线程更新状态
    entity.update(cx, |state, cx| {
        state.jobs[job_id].status = result;
        cx.notify();
    }).ok();
}))
.detach();
```

### 3.2 进度回传：mpsc channel

批量任务的进度（整体进度 + 单个任务进度）通过 **mpsc channel** 从后台回传到 UI 层。这是 Rust 批量处理的标准模式，`qubit-progress` 等库都采用 ChannelProgress 设计。

```rust
pub enum ProgressEvent {
    JobStarted { job_id: usize, name: String },
    JobProgress { job_id: usize, percent: f32 },
    JobCompleted { job_id: usize, output: PathBuf },
    JobFailed { job_id: usize, error: String },
    BatchCompleted { total: usize, success: usize, failed: usize },
}
```

后台任务通过 `tx.send(ProgressEvent::...)` 发送事件，UI 层在 `cx.spawn()` 中循环接收并更新状态。

### 3.3 UI 进度组件

`gpui-component` 提供了 **Progress 组件**（线性进度条），支持自动值钳制和过渡动画。批量场景下建议使用**双层进度**：

- **整体进度条**：已完成任务数 / 总任务数
- **每任务进度条**：在 DataTable 的每一行中显示单个文件的转换进度

## 四、任务取消

### 4.1 取消机制设计

GPUI 的任务在 **Drop 时自动取消**。但批量场景需要**用户主动触发取消**，这需要显式的 `CancellationToken`：

```toml
[dependencies]
tokio-util = { version = "0.7", features = ["rt"] }
```

```rust
use tokio_util::sync::CancellationToken;

// UI 层
struct BatchState {
    cancel_token: CancellationToken,
    // ...
}

// 用户点击"取消全部"
fn cancel_all(&mut self) {
    self.cancel_token.cancel();
    // UI 状态更新：所有 Running/Pending 任务标记为 Cancelled
}
```

每个任务的执行循环需要**在关键点检查取消信号**：

```rust
fn convert_rar_to_zip(
    rar_path: &Path,
    zip_path: &Path,
    cancel: &CancellationToken,
) -> Result<()> {
    let mut archive = unrar_ng::Archive::new(rar_path)?;

    for entry in archive.iter()? {
        if cancel.is_cancelled() {
            // 清理不完整的输出文件
            let _ = std::fs::remove_file(zip_path);
            return Err(anyhow!("Cancelled by user"));
        }
        // 解压 entry...
    }
    Ok(())
}
```

**重要：** 取消后必须**清理不完整的输出文件**，否则会留下损坏的 ZIP。或者采用 `ripzip` 的原子写入策略（先写临时文件，完成后 rename），天然避免这个问题。

### 4.2 取消后的 UI 状态

取消是"软取消"：正在执行的任务会在下一个检查点退出，已完成的文件保留，未开始的任务直接标记为 Cancelled，不产生输出文件。

## 五、错误处理与失败隔离

### 5.1 批量场景的错误策略

**单个任务失败不应该中断整个批次。** 每个任务独立执行，失败时记录错误并继续处理后续任务。这与传统的 `?` 传播错误不同，批量处理需要**收集所有错误后统一报告**：

```rust
pub struct BatchReport {
    pub total: usize,
    pub succeeded: Vec<JobSuccess>,
    pub failed: Vec<JobFailure>,
    pub cancelled: Vec<usize>,
}

pub struct JobFailure {
    pub job_id: usize,
    pub rar_path: PathBuf,
    pub error: String,
}
```

批量完成后，UI 弹出一个摘要对话框，展示成功/失败/取消的数量，并提供"重试失败项"按钮。

### 5.2 错误分类与用户提示

| 错误类型 | 用户提示 | 可否重试 |
|---|---|---|
| 源文件不存在/被占用 | "文件不存在或正被其他程序使用" | 可重试 |
| RAR 损坏 | "压缩文件已损坏，无法读取" | 不可重试 |
| 目标路径无权限 | "无法写入目标目录，请检查权限" | 可重试 |
| 磁盘空间不足 | "磁盘空间不足" | 可重试 |
| 文件名编码异常 | "文件名包含无法识别的字符" | 可重试（降级编码） |

### 5.3 失败重试

`batch-mode-batch-reconciliation` 等库提供了 `retry_failed_requests` 模式，对失败的任务进行有限次数的自动重试（如 2 次），适用于临时性错误（文件被短暂占用、网络驱动器瞬时不可用）。对于你的工具，建议**不自动重试**，而是让用户手动点击"重试失败项"，避免在文件持续损坏时浪费资源。

## 七、批量处理的性能考量

### 7.1 内存控制

批量处理时，**不要同时把所有 RAR 解压到内存**。采用**流式处理**：边解压边写入 ZIP，每个任务的内存占用控制在单个文件块的大小（如 8–64 MB）。`ripzip` 的自适应内存管理策略——根据系统可用 RAM 动态调整内存压缩阈值（小文件走内存，大文件走临时文件）——是值得参考的设计。

### 7.2 磁盘 I/O 竞争

批量并发时，多个任务同时读写磁盘会造成 I/O 竞争。如果源文件和目标目录在同一块物理磁盘上，**并发数过高反而会降低总吞吐量**。建议：

- 默认并发数 = `min(物理核数, 2)`，保守起步
- 在设置中暴露"并发数"选项，让高级用户手动调整
- 对于 HDD 用户，建议并发数设为 1–2；SSD 用户可以设得更高

### 7.3 大批量场景的 UI 虚拟滚动

如果用户一次拖入几百个 RAR 文件，DataTable 必须使用**虚拟滚动**，只渲染可见行。`gpui-component` 的 DataTable 和 VirtualList 组件默认支持虚拟滚动，即使几千个条目也能保持 120 FPS。

**总结：** 批量处理的引入主要在**调度层**——用 Tokio 的 `Semaphore` 控制并行度，用 `CancellationToken` 实现协作式取消，用 mpsc channel 回传进度。单任务内部的 ZIP 打包可以选用 `ripzip` 或 `mtzip` 获得 rayon 并行加速。UI 层用 GPUI 的 `background_spawn` + `then(cx.spawn(...))` 链式模式保证主线程流畅。整体架构不复杂，但取消后的文件清理和批量失败隔离是两个容易被忽略的细节，需要在实现时专门处理。
