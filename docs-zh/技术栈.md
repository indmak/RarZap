## 二、UI 层

### 2.1 GPUI 框架

GPUI 是 Zed 编辑器团队开发的 Rust 原生 UI 框架，采用**混合架构**：声明式视图树 + 立即模式特性，底层直接调用 GPU 渲染（macOS 用 Metal，Windows 用 DirectX，Linux 用 Vulkan）。

**核心优势：**
- 120 FPS 流畅渲染，大文件列表滚动无卡顿
- 声明式 API，写法接近 React + Tailwind 的组合体验
- 完全编译为原生二进制，**无 WebView 依赖**，部署极其干净
- 社区已有商业化应用验证（如 Longbridge Pro）

**需要注意：**
- 仍处于 **pre-1.0** 阶段，API 可能有不兼容变更
- 文档相对较少，部分场景需要参考 Zed 源码
- Linux 端依赖 libxcb、libxkbcommon 等系统库

**Cargo.toml 核心依赖：**
```toml
[dependencies]
gpui = "0.2.2"
gpui-component = "0.5.1"
```

### 2.2 UI 组件库：gpui-component

gpui-component 是 GPUI 生态中最成熟的组件库，提供 **60+ 跨平台桌面 UI 组件**，涵盖表单、导航、弹层、反馈、布局等类别，风格受 macOS/Windows 原生控件启发，结合 shadcn/ui 的现代设计。

**你的工具会用到的组件：**
- **Button / IconButton** — 选择文件、开始转换按钮
- **ProgressBar** — 转换进度显示
- **DataTable / VirtualList** — 待转换文件列表（支持虚拟滚动，即使几千个文件也不卡）
- **Dialog / Modal** — 错误提示、确认对话框
- **Input** — 输出路径输入框

架构上分为两层：`gpui-component` 提供开箱即用的样式化组件，`gpui-base` 提供无样式的基础行为与状态管理，你可以按需选择。

## 三、文件处理层

### 3.1 RAR 解压：unrar-ng

RAR 格式只能解压、不能创建（RAR 压缩算法是专有格式），所以你的工具流程是：**解压 RAR → 重新打包为 ZIP**。

unrar-ng 是活跃维护的 `unrar` crate 分支，核心改进是新增了**批量解压 API（`extract_all`）**，使用与原生 `unrar` CLI 相同的遍历循环，消除了逐文件 API 的冗余头部遍历开销。

**性能对比（Linux 内核源码 ~94,000 个文件）：**

| 后端 | 耗时 |
|---|---|
| 原生 `unrar` CLI | 7.15s |
| 原版 `unrar` crate | **70.69s** |
| **`unrar-ng`（`extract_all`）** | **6.88s** |



差距接近 **10 倍**，对于批量转换场景（用户可能一次拖入几十个 RAR），这个性能差异非常关键。

```toml
[dependencies]
unrar-ng = "0.7"
```

```rust
use unrar_ng::Archive;
```

**注意：** 0.7 版本将库名从 `unrar` 改为 `unrar_ng`，需要更新 `use` 语句。

### 3.2 ZIP 打包：zip crate

`zip` crate 是 Rust 生态中读写 ZIP 文件的标准库，支持 stored（无压缩）、deflate、bzip2、zstd 等压缩格式，基于 PKWARE APPNOTE v6.3.9 规范实现。

```toml
[dependencies]
zip = "3"
```

**压缩格式建议：** 对于压缩文件转换场景，推荐使用 **Deflate** 作为默认格式（兼容性最好，Windows/macOS/Linux 原生解压工具都支持）。如果追求更高压缩率，可以暴露 Zstd 选项让用户选择，但需注意 Windows 资源管理器原生不支持 Zstd。

### 3.3 文件对话框与系统集成

GPUI 提供了原生文件对话框 API，**不需要自己实现文件选择器**：

- `prompt_for_paths()` — 打开系统文件选择器（支持多选），返回 `Future`，用 `cx.spawn()` 异步等待用户选择
- `prompt_for_new_path()` — 打开“另存为”对话框
- `reveal_path()` — 在文件管理器中高亮文件（Finder / Explorer / Nautilus）
- `open_with_system()` — 用默认程序打开文件

在 Linux 上，GPUI 通过 **ashpd 桌面门户**（XDG Desktop Portal）调用原生文件对话框，在 GNOME/KDE 下表现与系统一致。

**典型的文件选择代码模式：**

```rust
cx.spawn(|this, mut cx| async move {
    let paths = this.update(&mut cx, |this, cx| {
        cx.prompt_for_paths(PromptOptions::default())
    }).await?;
    // 处理用户选择的 RAR 文件路径
}).detach();
```

## 四、构建与打包

### 4.1 各平台构建前提

| 平台 | 构建依赖 | 工具链 |
|---|---|---|
| **macOS** | Xcode.app（Metal 着色器编译需要，仅 Command Line Tools 不够） | `x86_64-apple-darwin` / `aarch64-apple-darwin` |
| **Windows** | Visual Studio Build Tools | `x86_64-pc-windows-msvc` |
| **Ubuntu/Debian** | GTK3 开发库、Vulkan 驱动、libxcb、libxkbcommon | `x86_64-unknown-linux-gnu` |



**Ubuntu 24.04 验证过的依赖安装命令：**
```bash
sudo apt update
sudo apt install -y gcc g++ clang libfontconfig-dev libwayland-dev \
  libxkbcommon-x11-dev libx11-xcb-dev libxcb1-dev libxkbcommon-dev \
  libssl-dev libzstd-dev libvulkan1 vulkan-validationlayers
```



**Rust 版本要求：** Linux 平台依赖 `oo7 0.6.0`，明确要求 **Rust 1.92 或更高版本**。

### 4.2 各平台打包格式

| 平台 | 内部测试/手动分发 | 面向用户的安装方式 |
|---|---|---|
| **macOS** | `.app` 或含 `.app` 的归档 | 已签名 + 已公证的 `.dmg` |
| **Windows** | 含 `.exe` 和资源的 `.zip` | **Inno Setup** 制作的安装程序（带卸载流程） |
| **Ubuntu/Debian** | 含可执行文件和资源的 `.tar.gz` | **`.deb` 包** |



**构建命令：**
```bash
cargo build --release --locked
```

`--locked` 确保使用已提交的 `Cargo.lock`，不会自动更新依赖。

### 4.3 关键注意事项

**macOS 公证是强制性的。** 从 macOS 10.15 起，未公证的应用无法在用户机器上直接运行。你需要 Apple Developer 账号，通过 `notarytool` 提交公证。

**Linux 运行时依赖要单独验证。** 开发机上安装的 `-dev` 包是构建依赖，最终用户机器上只需要运行时库。特别要检查 **Vulkan 驱动**是否存在于目标机器上（Ubuntu/Debian 桌面版通常自带）。

**打包前必须做的检查清单：**
1. 在目标平台构建机上运行 `cargo build --release --locked`，确认窗口能正常打开
2. 将二进制、外部资源、许可文本放入独立暂存目录
3. 确认应用标识（bundle identifier）、版本号、架构正确
4. 清理 `target/release` 中的调试符号和中间文件

## 五、错误处理与日志

### 5.1 错误处理策略

采用 **anyhow + thiserror** 的组合方案：

- **应用层**（UI 交互、文件操作流程）用 **anyhow** 的 `Result<T>` + `?` 传播，配合 `.with_context()` 附加人类可读的错误信息
- **库层/模块边界**（如压缩转换核心逻辑）用 **thiserror** 定义自定义错误枚举，便于上层分类处理

```rust
use anyhow::{Context, Result};

fn convert_rar_to_zip(rar_path: &Path, zip_path: &Path) -> Result<()> {
    let archive = unrar_ng::Archive::new(rar_path)
        .with_context(|| format!("无法打开 RAR 文件: {}", rar_path.display()))?;
    // ... 解压并打包逻辑
}
```

错误链的输出示例：
```
Error: 转换失败
Caused by:
  0: 无法打开 RAR 文件: /home/user/test.rar
  1: No such file or directory (os error 2)
```



### 5.2 日志系统

使用 **tracing** + **tracing-appender** 实现结构化日志，按日轮转，保留最近 7 天：

```toml
[dependencies]
tracing = "0.1"
tracing-appender = "0.2"
tracing-subscriber = { version = "0.3", features = ["env-filter"] }
```

日志文件位置：
- **Windows**: `%APPDATA%/YourApp/logs/`
- **macOS**: `~/Library/Logs/YourApp/`
- **Linux**: `~/.local/share/YourApp/logs/`

关键日志点：RAR 打开、解压进度、ZIP 写入、文件选择、错误发生。

## 六、测试策略

GPUI 提供了 `TestAppContext`，可以在**不需要真实 GPU/OS 环境**的情况下运行 UI 逻辑测试。测试分为三层：

| 测试层级 | 工具 | 覆盖内容 |
|---|---|---|
| **单元测试** | `cargo test` | 压缩转换核心逻辑（RAR→ZIP 的文件读写） |
| **集成测试** | `rstest-bdd` + GPUI TestAppContext | UI 状态变更、文件选择流程、进度更新 |
| **基准测试** | `gpui-bench` | 大文件列表渲染性能、转换吞吐量 |



**测试原则：** GPUI 测试应使用 **GPUI executor 的定时器**，而非 `smol::Timer` 等外部定时器，确保调度确定性。

## 七、CI/CD

使用 **GitHub Actions** 实现三平台自动构建。GPUI 社区已有成熟的 CI 工作流参考（gpui-component 的 `ci.yml`）。

**CI 矩阵：**
```yaml
strategy:
  matrix:
    include:
      - os: macos-latest
        target: aarch64-apple-darwin
      - os: macos-latest
        target: x86_64-apple-darwin
      - os: windows-latest
        target: x86_64-pc-windows-msvc
      - os: ubuntu-24.04
        target: x86_64-unknown-linux-gnu
```

**流水线步骤：**
1. 安装平台依赖（Linux 需额外安装系统库）
2. `cargo build --release --locked`
3. `cargo test`
4. 打包产物（macOS 签名公证 / Windows Inno Setup / Linux .deb）
5. 上传 artifact 或创建 GitHub Release

**注意：** 每个平台和架构必须**分别构建、分别测试**，macOS ARM64 与 x86_64 的二进制不能互换。

## 九、风险与缓解

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| GPUI API 不稳定 | 升级时可能需改动代码 | 锁定 `Cargo.lock`，仅在需要新功能时升级并预留迁移时间 |
| Linux 桌面环境差异 | GNOME/KDE 下文件对话框行为可能不同 | 通过 XDG Portal 统一；在 Ubuntu 24.04 + GNOME、KDE 各测一次 |
| 大 RAR 文件内存占用 | 解压 10GB+ 文件可能 OOM | 使用流式解压，边解压边写入 ZIP，不一次性加载到内存 |
| 文件名编码问题 | 中文/日文文件名在 RAR 中可能乱码 | 显式处理 CP437/UTF-8 编码转换 |
| macOS 公证流程复杂 | 首次配置耗时 | 提前申请 Apple Developer 账号，参考 notarytool 文档 |

---

**总结：** GPUI + unrar-ng + zip crate 这条技术链路是通的，CoZip 项目已经用 GPUI 做过压缩工具的先例。你的工具逻辑简单（解压→重打包），界面也不复杂，GPUI 的组件库完全够用。主要投入在打包发布环节（三平台的签名、公证、安装包制作），建议尽早把 CI 流水线搭起来，避免发布时手忙脚乱。
